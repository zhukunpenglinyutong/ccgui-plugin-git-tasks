状态机：球在谁手里

状态不靠人工维护，每次同步都按下面的规则从 GitHub 事实重新推算。只看“你”的审查（gh 当前登录账号，可加附加账号），其他人的审查只在流转记录里展示。看板上的五列就是这几个状态。

转换表（GitHub 事实）

从触发事件到
—作者打开 PR（非草稿）；草稿转 Ready for review待审查
待审查我提交 Request changes；我提交 Comment 类 Review可配置待修复
待审查我 Approve已通过
待修复PR head SHA 与我上次审查时的 SHA 不同（推送 / force-push / rebase 都能识别）；作者重新请求我审查可配置；作者回复评论可配置，默认关。仅“合并主干”的提交可忽略可配置待复审
待复审我再次 Request changes（轮次 +1）待修复
待复审我 Approve已通过

任意合并 / 关闭已合并 / 已关闭

看板拖拽 = 在本地记一笔（不写 GitHub）

拖拽记下的是一条“本地事件”，和 GitHub 事件放在同一条时间线上一起推算。所以拖完之后作者再推送，PR 照样会自己流到「待复审」，不会被你的拖拽“钉死”。每次拖拽都能撤销。

拖到记下的本地标记效果 / 限制
待审查撤回结论，重新审查回到待审查，之前的审查轮次保留
待修复看过了 · 需要修复相当于一次 Request changes（适合你在 GitHub 之外看过，比如本地跑了一下）
待复审作者已修复（你确认）适合作者在群里说“改好了”但还没推送的情况；只有你审过的 PR 才能拖进来
已通过看过了 · 没问题相当于一次 Approve
已结束标记完成不再提醒；作者之后有新推送会自动失效、回到正常流转；拖回去即取消
同一列—只调整顺序，只影响你自己看
已合并 / 已关闭 / 草稿 由 GitHub 决定，不能拖；拖不进去的列会变灰并写明原因

几个关键约定

以 SHA 为准，不以时间为准

“作者改了没有”= 当前 head SHA ≠ 我最后一次审查时 Review 绑定的 commit。提交时间可能早于审查（rebase、本地攒提交），SHA 不会骗人。

状态是算出来的，不是存的

插件只存三样东西：同步下来的事件快照、你的本地标记（含拖拽）、worktree 绑定。每次同步或改设置都整体重算，不会出现“卡在审查中”的脏状态。

只看“你”

多维护者时，别人 Request changes 不会让 PR 离开你的“待审查”。详情里会展示别人的审查，供参考。

多仓库

跟踪多个仓库时，看板、统计、侧栏都按仓库合并显示，卡片和柱子用仓库颜色区分；顶部可以只看某一个仓库。颜色按设置里的仓库顺序固定分配，切换仓库不会换色。

每日统计口径

新增 = 当天创建的 PR（含草稿），按仓库分色堆叠；审查 = 当天你计入的审查次数，分首审 / 复审；作者修复 = 你要求修改后作者第一次更新；按设置的切日时间分天。

数据怎么来

每个仓库每次同步约 2 次 gh 调用：一次 gh api graphql 拉 open PR 的 reviews / commits / timeline，一次拉近 N 天已合并 / 关闭的 PR。增量按 updatedAt 判断。

渲染规则（宿主控制，插件改不了）

  • 位置固定：分支名之后、PR# 之前，就是截图红框处
  • 颜色只能从宿主状态色里选（随主题、暗色模式自动适配），不收任意 hex
  • 文字最多 6 个字，超出截断；tooltip 纯文本
  • 每行最多 2 个插件徽标；插件停用或卸载时自动清掉
  • 推送式：渲染路径不调用插件代码，插件同步完一次性 set
  • 已有的 ctx.workspaces.list()（host:workspace）已能拿到 worktree 的 branch / prNumber，但宿主不广播变更；新建 / 删除 worktree 后徽标要跟上，所以 onChange 是真正新增的部分

插件（github-tasks）推徽标

const badges = ctx.ui.registerWorktreeBadges({
  key: "pr-status", onClick: (wt) => openDetail(linkPr(wt)),
});
badges.onChange(apply);
onSynced(() => apply(badges.list()));

function apply(targets) {
  for (const wt of targets) {
    const pr = linkPr(wt);
    const st = pr && deriveStatus(pr, rules);
    const def = st && statusDefs[st.key];
    badges.set(wt.workspaceId, def?.showOnWorktree
      ? { label: def.label, tone: def.tone, tooltip: tip(pr, st) } : null);
  }
}

需要你拍板的点

稿子里都按“推荐”实现了，不同意的直接告诉我编号。

1

拖到「已结束」= 本地标记完成，作者再推送时怎么办？新

“完成”通常是“这个我不管了”。但如果作者之后又推送，大概率是有新东西需要你看。稿子里的做法：作者有新推送 / 重新请求审查时，完成标记自动失效，PR 回到正常流转。

推荐：有新推送就自动回来
2

跨列拖拽要不要先弹确认？新

拖拽不往 GitHub 写东西，只记本地标记，所以稿子里是直接生效 + 底部 5 秒“撤销”。拖之前列头会写明“放下 = 标记「看过了 · 需要修复」”。

推荐：不弹确认，给撤销
3

绑定已有 worktree，要不要写回客户端？新

稿子里绑定只存插件本地，侧栏只多出状态徽标，不会出现 PR# 紫色标签（那个是客户端从 PR 创建时记录的）。要显示的话需要宿主再加一个“给 worktree 记 PR 号”的接口。

推荐：先只存插件本地
4

仓库颜色怎么分配？新

按设置里仓库的顺序固定分配（蓝 / 橙 / 青……），切换筛选、停用某个仓库都不会让别的仓库换色。8 个仓库以内各一色，再多就合并成“其他”。

推荐：按顺序固定，最多 8 色
5

新插件和旧 git-tasks 的关系

新建 github-tasks（只读、轻量），接管侧栏「Git 任务管理」这个入口位置；旧 git-tasks 停用，旧数据不迁移。

推荐：新插件接管入口，旧插件停用
6

只留了 Comment 的 Review，算不算“要求修复”？

算的话进入待修复；不算的话留在待审查。#1439 就是这种情况，可在设置里切换看效果。

推荐：算
7

PR 下的普通评论（不是 Review）算不算审查过？

普通评论经常只是问问题，算进去会误判。

推荐：不算
8

只看我自己，还是团队任一维护者？

只看 gh 当前登录账号，另外允许加“附加账号”。

推荐：只看我 + 附加账号
9

Approve 之后作者又推送了，回到待复审吗？

回到待复审更安全；默认忽略“仅合并主干”的提交（#1426 就是这种）。

推荐：回到待复审 + 忽略合并主干
10

跟踪范围

默认所有 open PR；排除 dependabot / renovate 这类机器人和你自己开的 PR。

推荐：所有 open PR，排除机器人和自己
11

宿主接口：推送式 set，还是渲染时回调？

推送式不会在侧栏渲染时跑插件代码；代价是插件要监听 worktree 增删。

推荐：推送式
12

“每天”从几点算？

默认本地 0 点，可改成 4:00 / 6:00。

推荐：0 点，可配置
